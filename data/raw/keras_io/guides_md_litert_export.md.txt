Exporting Keras models to LiteRT.

Introduction.

LiteRT (formerly TensorFlow Lite) lets you run machine learning models on mobile devices, embedded systems, and browsers with low latency and small binary size.

Keras provides a built-in <code> API that converts your model to the LiteRT (<code>) format in a single line of code. This guide covers the complete workflow:

Export a Keras model to LiteRT.

Run inference with the LiteRT interpreter.

Handle different model types (Sequential, Functional, subclassed, multi-input).

Resize inputs at runtime.

Use the signature runner for named inputs and outputs.

Quantize the model for smaller size and faster inference.

We will use the PyTorch backend because it produces models that are fully compatible with the new LiteRT Android runtime — no flex ops, no deprecated interpreter APIs. The same <code> API also works with the TensorFlow backend, which we summarize in a dedicated section at the end.

Dynamic shapes and runtime input resizing.

LiteRT models exported from Keras have static shapes in the graph, but the interpreter supports runtime input resizing. This means you can process different batch sizes with the same exported model without re-exporting. Warning: The new <code> does not support graphs with dynamic shapes. Models exported with the PyTorch backend and a <code> argument may fail to run with this interpreter. If you need variable input shapes, use runtime input resizing (shown below) instead. Dynamic-shape export works when using the TensorFlow backend during conversion, but the resulting model should still be executed with a TFLite interpreter that supports dynamic tensors if you do not resize inputs to a fixed shape first.

Signature runner.

Use the signature runner for cleaner inference code. You can discover the input names for a signature via <code>; for models exported with the PyTorch backend they are typically <code>, <code>, etc.

Custom input signature.

You can override the inferred input signature by passing <code> to <code>. This is useful when you want to enforce specific shapes or dtypes. Note: <code> in an <code> shape (e.g., <code>) tells Keras that the dimension is unknown, but the exported LiteRT graph still uses a concrete batch size (1) for tracing. Use runtime resizing (shown above) to handle variable batch sizes at inference time.

Best practices.

Always test the exported model before deploying — run inference and compare outputs with the original Keras model.

Use the PyTorch backend for LiteRT export to avoid flex ops and ensure compatibility with the new LiteRT Android runtime.

Call subclassed models on sample data before <code> to build weights and infer the input signature.

Use runtime input resizing for variable batch sizes rather than <code>. Graphs with dynamic shapes are not supported by the new <code> and may fail when exported with the PyTorch backend.

Start with <code> for quick dynamic-range quantization on either backend.

Use <code> when you need finer control (channel-wise, symmetric, mixed-precision) or when targeting the PyTorch backend with Float16.

Keep models under 2 GB per TFLite file — LiteRT uses a flatbuffer format with a 2 GB limit per file. If your model is larger, use the <code> / <code> pipeline which shards the model into multiple sub-models inside a <code> container.
