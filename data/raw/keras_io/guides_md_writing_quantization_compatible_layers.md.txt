Writing Quantization-Compatible Layers in Keras.

What are quantization-compatible layers?

Keras lets you optimize models via post-training quantization (PTQ) by calling the <code> or <code> APIs. Keras exposes an extensible framework for defining quantization-compatible layers. This lets you author custom layers that plug into the quantization framework, can be quantized to INT8 or INT4, and saved/loaded with quantization metadata.

A quantization-compatible layer needs to implement a few hooks, so that it can:

Switch its variables to quantized representations.

Use a quantization-aware forward path at inference.

Save and load quantization metadata with the model.

In this guide, we'll implement a simple layer that supports INT8 PTQ. The same patterns generalize to INT4 quantization and FP8 mixed-precision training.

The hooks you'll implement.

At minimum, your layer should define:

<code>: Converts existing variables to quantized form and switches the dtype policy.

<code>: Allocates INT8 variables needed by your layer.

<code>: Minimal INT8 forward path.

We'll implement these for a very small layer called <code>, which multiplies the inputs by a trainable per-feature vector (elementwise scaling on the last dimension). The same patterns generalize to more sophisticated layers.

Practical tips.

Here are concrete patterns you can reuse when making your own layers PTQ-friendly.

Build-time vs call-time responsibilities.

In <code>, if <code> is set: allocate the quantized variables and skip allocating the float kernel to avoid duplicates.

Record any metadata you need for the call path, e.g., for INT4:

The axis you packed along (e.g., <code>).

The original (unpacked) length on that axis (e.g., <code> or <code>).

In quantized call hooks, compute with the quantized buffers and de-scale back to float at the end, wherever possible. This allows you to leverage optimized low-precision kernels (e.g., cuBLAS INT8 GEMM).

INT4 specifics (packed nibbles).

Quantize to INT4 values in range [-8, 7] (still dtype int8), then pack two 4-bit integers per byte with <code>.

Store the packed kernel with <code>. Unpack on the fly in the call path with <code>.

Keep the original length and pack axis so you can unpack for LoRA, gradients, and serialization.

Inputs quantization and broadcasting.

In the forward path de-scale outputs using <code>; make sure both scales broadcast to the output shape.

Dtype policy lifecycle.

During <code>: delete FP32 variables, allocate quantized ones, assign values, then set <code> before changing the dtype policy.

Only change policy if the current policy has <code> to avoid an infinite loop.

Serialization contract.

Provide a fixed-order logic for variable serialization so save/load is deterministic.

Write variables in a fixed order per mode (e.g., None: [kernel, bias], <code>: [kernel, bias, kernelscale], <code>: [kernel, bias, kernelscale]).

Validation and error handling.

Validate <code> early and raise a <code> for unsupported modes.

After quantization, run a tiny smoke test and assert the output matches the FP32 path and values are within a reasonable tolerance after de-scale.

Performance hygiene.

Avoid repeated transformations hot paths; precompute as much information as possible and keep the forward-pass hooks lightweight.

Keep quantized buffers <code> and prefer vectorized operations.
