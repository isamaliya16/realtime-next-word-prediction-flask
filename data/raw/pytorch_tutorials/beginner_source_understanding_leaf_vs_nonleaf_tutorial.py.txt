Leaf vs. non-leaf tensors.

This is a Directed Acyclic Graph (DAG) which keeps a record of input tensors (leaf nodes), all subsequent operations on those tensors, and the intermediate/output tensors (non-leaf nodes). The distinction between leaf and non-leaf determines whether the tensor’s gradient will be stored in the <code> property after the backward pass, and thus be usable for gradient descent. We’ll cover this some more in the following section.

Let’s now investigate how PyTorch calculates and stores gradients for the tensors in its computational graph.

<code>.

To build the computational graph which can be used for gradient calculation, we need to pass in the <code> parameter to a tensor constructor. By default, the value is <code>, and thus PyTorch does not track gradients on any created tensors. To verify this, try not setting <code>, re-run the forward pass, and then run backpropagation. It’s useful to remember that a non-leaf tensor has <code> by definition, since backpropagation would fail otherwise. If the tensor is a leaf, then it will only have <code> if it was specifically set by the user. Another way to phrase this is that if at least one of the inputs to a tensor requires the gradient, then it will require the gradient as well.

In summary, <code> tells autograd which tensors need to have their gradients calculated for backpropagation to work. This is different from which tensors have their <code> field populated, which is the topic of the next section.

<code>.

To actually perform optimization (e.g. SGD, Adam, etc.), we need to run the backward pass so that we can extract the gradients.

Calling <code> populates the <code> field of all leaf tensors which had <code>. The <code> is the gradient of the loss with respect to the tensor we are probing. Before running <code>, this attribute is set to <code>.

PyTorch returns <code> for the gradient and also warns us that a non-leaf node’s <code> attribute is being accessed. Although autograd has to calculate intermediate gradients for backpropagation to work, it assumes you don’t need to access the values afterwards. If we look at the state of the computational graph now, we see that the <code> attribute has changed for the intermediate tensors. By convention, this attribute will print <code> for any leaf node, even if it requires its gradient.

If you call <code> on a leaf tensor, it results in a no-op since leaf tensors already retain their gradients by default (when <code>). If we call <code> on a tensor that has <code>, PyTorch actually throws an error, since it can’t store the gradient if it is never calculated.
