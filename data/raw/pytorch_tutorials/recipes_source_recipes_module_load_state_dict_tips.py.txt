Using <code> First, let us consider what happens when we load the checkpoint with <code>. When we save a checkpoint with <code>, tensor storages are tagged with the device they are saved on. With <code>, tensor storages will be loaded to the device they were tagged with (unless this behavior is overridden using the <code> flag). For ease of explanation, let us assume that the tensors were saved on CPU. This means that on the first line all tensor storages will be loaded into CPU RAM, which can be undesirable when:

CPU RAM is smaller than the size of the checkpoint.

Waiting for the entire checkpoint to be loaded into RAM before performing, for example, some per-tensor processing.

The <code> keyword argument to <code> attempts to solve the above two problems. As its name implies, the <code> keyword argument to <code> makes use of an mmap call which maps a file on disk into virtual memory and lets the OS handle loading and unloading into physical memory automatically. When this flag is passed, tensor storages will be memory-mapped.

<code> is usually implemented via an in-place <code>. This means that the parameter/buffer with the corresponding key in the state dictionary is copied into the parameter/buffer in the <code>.

However, an in-place copy into a tensor on the <code> device is a no-op. In order to avoid this, we can pass the <code> keyword argument to <code>.

A caveat here is that since optimizers hold a reference to <code>, the optimizer must be initialized after the module is loaded from state dict if <code> is passed.
