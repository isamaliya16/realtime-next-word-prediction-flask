This guide provides an overview and examples of a modeling code shim) that you can employ to use your existing TF1.x models in TF2 workflows such as eager execution, <code>, and distribution strategies with minimal changes to your modeling code.

Scope of usage.

The shim described in this guide is designed for TF1.x models that rely on:

<code> and <code> to control variable creation and reuse, and.

Graph-collection based APIs such as <code>, <code>, <code>, and <code> to keep track of weights and regularization losses.

This includes most models built on top of <code>, <code> APIs, and TensorFlow-Slim.

The shim is NOT necessary for the following TF1.x models:

Stand-alone Keras models that already track all of their trainable weights and regularization losses via <code> and <code> respectively.

<code>s that already track all of their trainable weights via <code>, and only create weights if they have not already been created.

These models are likely to work in TF2 with eager execution and <code>s out-of-the-box.

Import TensorFlow and other dependencies.

The <code> decorator.

The key shim described in this guide is <code>, a decorator that you can use within methods belonging to <code> and <code> to track TF1.x-style weights and capture regularization losses.

Decorating a <code>'s or <code>'s call methods with <code> allows variable creation and reuse via <code> (and by extension <code>) to work correctly inside of the decorated method rather than always creating a new variable on each call. It will also cause the layer or module to implicitly track any weights created or accessed via <code> inside the decorated method.

In addition to tracking the weights themselves under the standard <code>/<code>/etc. properties, if the method belongs to a <code>, then any regularization losses specified via the <code> or <code> regularizer arguments will get tracked by the layer under the standard <code> property.

This tracking mechanism enables using large classes of TF1.x-style model-forward-pass code inside of Keras layers or <code>s in TF2 even with TF2 behaviors enabled.

Variable-scope based variable reuse.

Any variable creations in the forward pass based on <code> will maintain the same variable naming and reuse semantics that variable scopes have in TF1.x. This is true as long as you have at least one non-empty outer scope for any <code> with auto-generated names, as mentioned above.

Note: Naming and reuse will be scoped to within a single layer/module instance. Calls to <code> inside one shim-decorated layer or module will not be able to refer to variables created inside of layers or modules. You can get around this by using Python references to other variables directly if need be, rather than accessing variables via <code>.

Eager execution & <code>.

As seen above, decorated methods for <code> and <code> run inside of eager execution and are also compatible with <code>. This means you can use pdb and other interactive tools to step through your forward pass as it is running.

Warning: Although it is perfectly safe to call your shim-decorated layer/module methods from inside of a <code>, it is not safe to put <code>s inside of your shim-decorated methods if those <code> contain <code> calls. Entering a <code> resets <code>s, which means the TF1.x-style variable-scope-based variable reuse that the shim mimics will break down in this setting.

Distribution strategies.

Calls to <code> inside of <code>-decorated layer or module methods use standard <code> variable creations under the hood. This means you can use them with the various distribution strategies available with <code> such as <code> and <code>.

Guidance on variable names.

Explicit <code> calls and Keras layers use a different layer name / variable name autogeneration mechanism than you may be used to from the combination of <code> and <code>. Although the shim will make your variable names match for variables created by <code> even when going from TF1.x graphs to TF2 eager execution & <code>, it cannot guarantee the same for the variable names generated for <code> calls and Keras layers that you embed within your method decorators. It is even possible for multiple variables to share the same name in TF2 eager execution and <code>.

You should take special care with this when following the sections on validating correctness and mapping TF1.x checkpoints later on in this guide.

Incremental migration to Native TF2.

As mentioned earlier, <code> allows you to mix TF2-style object-oriented <code>/<code>/<code> usage with legacy <code>/<code>-style usage inside of the same decorated module/layer.

This means that after you have made your TF1.x model fully-TF2-compatible, you can write all new model components with native (non-<code>) TF2 APIs and have them interoperate with your older code.

However, if you continue to modify your older model components, you may also choose to incrementally switch your legacy-style <code> usage over to the purely-native object-oriented APIs that are recommended for newly written TF2 code.

<code> usage can be replaced with either <code> calls if you are decorating a Keras layer/model, or with <code> calls if you are decorating Keras objects or <code>s.

Both functional-style and object-oriented <code> can generally be replaced with the equivalent <code> layer with no argument changes required.

You may also consider chunks parts of your model or common patterns into individual layers/modules during your incremental move to purely-native APIs, which may themselves use <code>.

A note on Slim and contrib.layers.

A large amount of older TF 1.x code uses the Slim library, which was packaged with TF 1.x as <code>. Converting code using Slim to native TF 2 is more involved than converting <code>. In fact, it may make sense to convert your Slim code to <code> first, then convert to Keras. Below is some general guidance for converting Slim code.

Ensure all arguments are explicit. Remove <code> if possible. If you still need to use them, split <code> and <code> into their own layers.

Separable conv layers map to one or more different Keras layers (depthwise, pointwise, and separable Keras layers).

Slim and <code> have different argument names and default values.

Note that some arguments have different scales.

Maintaining checkpoint compatibility during migration to Native TF2.

The above migration process to native TF2 APIs changed both the variable names (as Keras APIs produce very different weight names), and the object-oriented paths that point to different weights in the model. The impact of these changes is that they will have broken both any existing TF1-style name-based checkpoints or TF2-style object-oriented checkpoints.

However, in some cases, you might be able to take your original name-based checkpoint and find a mapping of the variables to their new names with approaches like the one detailed in the Reusing TF1.x checkpoints guide.

Handling TF1.x to TF2 behavior changes not covered by the modeling shims.

The modeling shims described in this guide can make sure that variables, layers, and regularization losses created with <code>, <code>, and <code> semantics continue to work as before when using eager execution and <code>, without having to rely on collections.

This does not cover all TF1.x-specific semantics that your model forward passes may be relying on. In some cases, the shims might be insufficient to get your model forward pass running in TF2 on their own. Read the TF1.x vs TF2 behaviors guide to learn more about the behavioral differences between TF1.x and TF2.
