TensorFlow 2.x includes many API changes from TF 1.x and the <code> APIs, such as reordering arguments, renaming symbols, and changing default values for parameters. Manually performing all of these modifications would be tedious and prone to error. To streamline the changes, and to make your transition to TF 2.x as seamless as possible, the TensorFlow team has created the <code> utility to help transition legacy code to the new API.

Note: <code> is installed automatically for TensorFlow 1.13 and later (including all TF 2.x builds).

Typical usage is like this:

tfupgradev2 \ --intree myproject/ \ --outtree myproject_v2/ \ --reportfile report.txt.

It will accelerate your upgrade process by converting existing TensorFlow 1.x Python scripts to TensorFlow 2.x.

The conversion script automates many mechanical API transformations, though many APIs cannot be automatically migrated. It is also not able to fully make your code compatible with TF2 behaviors and APIs. So, it is only a part of your migration journey.

Compatibility modules.

Certain API symbols can not be upgraded simply by using a string replacement. Those that cannot be automatically upgraded will be mapped to their locations in the <code> module. This module replaces TF 1.x symbols like <code> with the equivalent <code> reference. If you are already using <code> APIs by importing TF via <code>, the <code> script will attempt to convert these usages to the non-compat APIs where possible. Note that while some <code> APIs are compatible with TF2.x behaviors, many are not. Therefore, it's recommended to manually proofread replacements and migrate them to new APIs in the <code> namespace instead of <code> namespace as quickly as possible.

Because of TensorFlow 2.x module deprecations (for example, <code> and <code>), some changes can not be worked around by switching to <code>. Upgrading this code may require using an additional library (for example, <code>) or switching to a package in tensorflow/addons.

Recommended upgrade process.

The rest of this guide demonstrates how to use the symbol-rewriting script. While the script is easy to use, it is strongly recommended that you use the script as part of the following process:

Unit Test: Ensure that the code you’re upgrading has a unit test suite with reasonable coverage. This is Python code, so the language won’t protect you from many classes of mistakes. Also ensure that any dependency you have has already been upgraded to be compatible with TensorFlow 2.x.

Install TensorFlow 1.15: Upgrade your TensorFlow to the latest TensorFlow 1.x version, at least 1.15. This includes the final TensorFlow 2.0 API in <code>.

Test With 1.15: Ensure your unit tests pass at this point. You’ll be running them repeatedly as you upgrade so starting from green is important.

Run the upgrade script: Run <code> on your entire source tree, tests included. This will upgrade your code to a format where it only uses symbols available in TensorFlow 2.0. Deprecated symbols will be accessed with <code>. These will eventually require manual attention, but not immediately.

Run the converted tests with TensorFlow 1.15: Your code should still run fine in TensorFlow 1.15. Run your unit tests again. Any error in your tests here means there’s a bug in the upgrade script. Please let us know.

Check the upgrade report for warnings and errors: The script writes a report file that explains any conversions you should double-check, or any manual action you need to take. For example: Any remaining instances of contrib will require manual action to remove. Please consult the RFC for more instructions.

Install TensorFlow 2.x: At this point it should be safe to switch to TensorFlow 2.x binaries, even if you are running with legacy behaviors.

Test with <code>: Re-running your tests with a <code> in the tests' main function should give the same results as running under 1.15.

Enable V2 Behavior: Now that your tests work using the TF2 binaries, you can now begin migrating your code to avoiding <code>s and only using supported TF2 behaviors (with no TF2 behavior disabling). See the Migration guides for details.

Caveats.

Do not update parts of your code manually before running this script. In particular, functions that have had reordered arguments like <code> or <code> cause the script to incorrectly add keyword arguments that mismap your existing code.

The script assumes that <code> is imported using <code>, or <code>.

This script does not reorder arguments. Instead, the script adds keyword arguments to functions that have their arguments reordered.
